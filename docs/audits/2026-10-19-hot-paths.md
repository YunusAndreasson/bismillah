# Editing and scrolling performance audit (2026-10-19)

Two changes reduce work while writing: table previews now move their existing grids
during ordinary prose edits, and background word counting reuses unchanged lines.
In the measured 1 MB book, synchronous prose edits fell from 12 ms to 10 ms at the
median. Scrolling was essentially unchanged. Long-document typing still has slow
frames, especially on lines containing inline code.

## Measurements

The real Tauri app ran through `scripts/headless.sh` and `tauri-driver`, using
WebKitGTK and software rendering under Xvfb at 2× scale. Both binaries used the same
debug profile with the production frontend embedded. These are controlled local
comparisons, not new release-budget results. The release measurements in
ARCHITECTURE.md §14 remain historical results, and its unmet budgets remain open.

The baseline is the app built before this investigation, including the author's
existing code-quality changes. It was copied before rebuilding. Its embedded frontend
asset hashes were checked against a fresh Vite build of the current source with only
the two production changes reverted in a scratch copy: `index-Cdjg1QVn.js`,
`render-B5-miDVD.js` and `index-D8gEARSV.css` all match. SHA-256:

- Before: `f1a10ebba00b471b2bf532dd442931d76ce556912e77bba188607df5126491af`
- After: `0997b0f819537bda66d5c67202cc2a83f9af8dc9be3687e4398b53110d814901`

The final before and after runs were sequential, with no simultaneous build or test
run. The book repeats the bundled guide and specimen to 1.01 MB (175,288 words),
including Arabic, mixed-script prose, tables, images and inline code. Checking,
autosave and typewriter scrolling stayed enabled. Host load and software rendering
vary, so small differences and tail latencies need care.

| Real-app measurement | Before median / p95 | After median / p95 | Baseline recheck median / p95 |
| --- | --- | --- | --- |
| Short-document typing, key to painted frame | 15 / 30 ms | 22 / 34 ms | 18 / 29 ms |
| 1 MB prose typing, key to painted frame | 31 / 44 ms | 30 / 55 ms | 32 / 50 ms |
| 1 MB inline-code line typing, key to painted frame | 35 / 51 ms | 38 / 74 ms | 37 / 62 ms |
| 1 MB prose edit, synchronous dispatch | 12 / 16 ms | 10 / 14 ms | 13 / 16 ms |
| 1 MB inline-code line edit, synchronous dispatch | 17 / 20 ms | 16 / 20 ms | 16 / 18 ms |
| 1 MB line-break insertion, synchronous dispatch | 15 / 21 ms | 14 / 18 ms | 14 / 16 ms |
| Scrolling 1 MB, animation-frame interval | 16 / 25 ms | 16 / 23 ms | 17 / 33 ms |

These results establish less synchronous prose-edit work, not an overall
input-to-paint improvement. In the final run the short-document control also became
slower, and long-document tail latencies worsened. Frame scheduling and background
work remain variable; the raw results retain these unfavorable samples. Repeating
the unchanged baseline after the final build also shifted its timings (third column).
That supports treating small paint differences cautiously, but does not demonstrate
that the final build's worse tail latencies are harmless. The retained improvements
are reduced synchronous prose-edit work and segmentation CPU; the typing budget
remains open.

Typing uses 280 real key events per case, in eight bursts separated by 700 ms so
saving, checking and counts run between bursts. Synchronous edits insert and remove
text at the same place, with an animation frame between pairs: 50 samples after 10
warm-up pairs. They measure transaction work, not input-to-paint latency. Scrolling
advances `scrollTop` by 120 CSS pixels per animation frame, for 180 frames, discarding
the first 10; both runs reached 21,600 pixels. This tests the webview's scroll work,
not native touchpad event delivery.

The checker's first pass over the book remains active during these measurements;
waiting for every paragraph is unlike normal editing and can take minutes. The
scroll probe waits two seconds after launch before starting the editing cases.

The word-count comparison runs the actual old stateless counter and new cached
counter in **Node v26.12.0**, separately from the app's WebKit engine. For 30 edits
after priming the cache, full segmentation took **68 ms median / 81 ms p95**;
cached counting took **6 ms median / 7 ms p95**, about 91% less median CPU time.
Every count was checked against the original. This is a CPU microbenchmark,
not a claim that WebKit word counting has those exact timings. The repeated book
also favors reuse within the first count; normal documents still benefit from
unchanged lines on subsequent counts.

The count waits for a 300 ms typing pause. The typing probe's 700 ms pauses can let
both versions finish before the next burst, so this CPU ratio does not predict a
matching improvement in key-to-paint latency.

Resident memory across the app and WebKit processes at the end of inline-code typing
was 890 MiB before, 952 MiB after and 939 MiB in the baseline recheck. These snapshots
do not establish a memory change. The line cache adds memory proportional to distinct lines in
the current count.

## Changes retained

**Table previews (`src/editor/previewTables.ts`).** The existing fast path required
the reveal state's object identity to stay the same. Typing changes the revealed
block's end position, so that condition failed and tables were scanned and rebuilt
on ordinary keys. The new check compares the old block's boundaries mapped through
the changes with the new revealed block. Safe inline edits now only map the existing
decorations. A simultaneous selection move into a table still rebuilds and reveals
that table. Structural edits continue to use the conservative rebuild path.

The shared `inlineEdit` check also rejects reuse when the parsed tree has advanced
beyond its previous mapped coverage. A regression test reproduced a missing grid
when a background parse completed in the same transaction as a prose edit. Rebuilding
in that case also picks up newly parsed link definitions and images; subsequent
ordinary edits can use the fast path again.

**Word counts (`src/editor/wordCount.ts`, `src/core/workspace.svelte.ts`).** Previously
each 300 ms typing pause segmented the entire document again with `Intl.Segmenter`.
The workspace now keeps a counter that reuses totals for unchanged lines. Metadata
and URLs are removed from a temporary copy before splitting, so multiline titles
and frontmatter retain their existing treatment. Newlines delimit words in the
segmenter; Arabic diacritics, dictionary-segmented scripts and mixed text use the
same segmentation as before. Each count replaces the cache with only the current
lines, rather than accumulating deleted text or old documents. Neither change
rewrites the writer's document or alters saving.

**Repeatable probes (`scripts/perf.ts`).** `editing`, `scrolling` and `wordcount`
join the existing launch, typing and idle measurements. Raw samples can be saved
with `--out`, and the Node comparison is explicitly labelled separately.

## Experiment rejected

Image previews currently scan document lines on structural edits. An experiment
walked parsed image nodes instead, skipping code and tables. It passed correctness
tests but did not improve the measured inline-code and line-break paths: medians
were 22 → 23 ms and 19 → 21 ms in an earlier pair of runs. That experiment was
removed. The final code keeps the original image handling.

## Remaining opportunities

1. **Markdown parsing remains a major candidate for long-document typing.** The
   earlier Phase 6 audit isolated Lezer's top-level block traversal; the new results
   are consistent with that remaining limit, but do not newly attribute CPU time to
   it. Avoid replacing or bypassing the parser without testing Markdown structure,
   cursor motion and RTL behavior. The 1 MB inline-code p95 did not improve here.
2. **Structural preview invalidation is still broad.** Enter, fences, links, images
   and lines containing code can invalidate document-wide preview fields. A proper
   incremental index would need to handle reference definitions, parser progress,
   multiline structures and selection changes. The conservative path stays correct.
3. **Word counting still reads and filters the whole document.** Unchanged lines
   avoid segmentation, but text extraction, URL filtering, splitting and map lookups
   remain O(document length). One enormous physical line also needs segmentation
   again when edited. A worker or a correctly invalidated incremental index is a
   possible next step if this remains visible in larger documents.
4. **Initial checking remains background CPU work.** The scheduler prioritizes the
   viewport and limits batches, but `lintUnits` still traverses remaining sibling
   blocks after reaching its budget. Early traversal termination is worth a focused
   measurement. No checker or revision-handling change was made here.
5. **Scrolling already bounds most decoration work to visible ranges.** The
   16–17 ms medians and 23–33 ms p95 did not establish a scrolling improvement. The
   software-rendered harness cannot predict accelerated desktop touchpad latency;
   no scrolling behavior was changed to chase these numbers.

Saving and recovery still serialize the exact source and follow the existing
durability contract. Startup and library-idle fixes from Phase 6 were reviewed in
the prior audit; this investigation changes neither and makes no new budget claim.

## Validation

The targeted unit tests pass: table mapping through typing/deletion, a simultaneous
edit and caret move into a table, newly parsed tables/images/definitions arriving
during a prose edit, counts matching the original counter through
specimen/guide edits, multilingual text, multiline metadata and URLs, repeated
lines, and cache eviction between documents. A real-app regression also checks
the displayed count after typing, undo and opening another file.

Final `pnpm verify` passes on the guarded source: type checking, formatting and
typed ESLint; **355 frontend tests**; Rust formatting, Clippy, workspace tests and
dependency policy checks; **183 real-app tests across 18 suites**; and **16 visual
checks**. No visual baselines were rewritten. The built app's SHA-256 still matches
the measured final binary above.

Design review (DESIGN.md §18): **pass**. The real-app suites cover keyboard entry,
table reveal, caret motion and selection in Arabic and mixed text. Contrast tests
pass in both themes. The specimen's vocalised Arabic was inspected at 640, 1280,
1920 and 2560 CSS pixels in light and dark; mixed text was also inspected in a
short window with doubled writing size. Content hierarchy, file/mode status,
grouping, keyboard organization and typography retain their existing behavior.
Screenshots are in `/tmp/bismillah-hot-path-shots/`,
`/tmp/bismillah-hot-path-zoom-shots/` and `/tmp/bismillah-hot-path-final-shots/`.

The existing uncommitted code-quality changes were preserved. These performance
changes are left in the worktree for review; the personal 1.0 acceptance check in
PLAN.md remains pending.
