# Live idle CPU investigation — 2026-10-19

**Status: the native high-CPU trigger is confirmed: CodeMirror's caret-layer CSS
animation kept running while the window was unfocused.** A reversible live
steady-caret workaround reduced the author's running process to 0.1% main CPU and
0% WebKit CPU in a ten-second sample. The permanent bounded-blink implementation is
in the rebuilt app; final verification is recorded below. No document text was
read, edited, saved or closed during the native probes.

The quiet Xvfb benchmark alone did not establish native idle performance. The
native A/B/A comparison below provides the missing causal evidence.

## Live measurements

The existing process was PID 3078504, running on Wayland. Only process metadata,
CPU counters and function/code-address samples were collected. Its document was not
read, edited or closed. The debugger hid function argument values and disabled
symbol downloads. Privileged attachment was needed because ordinary attachment
was denied by the kernel's ptrace policy.

| Sample | Result |
|---|---|
| Ten-second process-family interval | Main 50.5% of one core; WebKit renderer 11.4%; network process 0% |
| Five-second thread interval | Main/UI thread 60.86%; ReceiveQueue 2%; other threads below the interval's counter resolution |
| Later ten-second interval | Main 6.7% user + 1.8% system CPU |
| Following fifteen-second interval | Main 43.8%; renderer 8.73% |

These intervals vary. They confirm excessive live CPU use; they do not establish
that it used an entire core throughout its lifetime. The supplied 56 CPU minutes
in three elapsed hours is approximately 31% of one core averaged over that period.

The window was on workspace 2, mapped, and unfocused when inspected; a later
inspection found the monitor on workspace 1. Historical visibility during every
CPU interval was not recorded. Visibility and focus remain variables to control.

The running executable had been replaced on disk. Its `/proc/PID/exe` copy has
SHA-256 `0997b0f819537bda66d5c67202cc2a83f9af8dc9be3687e4398b53110d814901`,
matching the earlier hot-path audit's final binary. At the initial investigation, the debug binary on disk had
SHA-256 `0552ac8107314984f0f4cb94aa76339ec1e62316e511f889caa115e6de4c5575`.
Rebuilding does not update an already running process. This fact alone does not
identify a fix in the newer build.

## CPU attribution

Ten brief debugger samples landed in `ppoll` through GLib/GTK's event loop. Those
pause-based samples did not explain the measured CPU use and are not evidence
that the high CPU report is false.

A bounded eight-second syscall-count trace recorded 330 `ppoll` calls, 380 `ioctl`
calls and 56 `poll` calls. This is not a tight loop making hundreds of thousands
of poll calls per second. The summary recorded no read/write payloads.

A ten-second CPU-clock sampling probe captured **238 user-space instruction
pointers**, with no lost records:

- 128 samples (53.8%) were in Pixman.
- 77 (32.4%) were in libc, mostly at a vectorised buffer-fill loop.
- 13 (5.5%) were in the application image.
- The remainder were scattered across GLib, GTK/GDK and other loaded libraries.

A second ten-second probe captured **111 CPU-time samples with call chains**, with
no lost records. The common chains run through GTK/GDK drawing, `cairo_fill` and
Pixman; another common chain runs through GDK/Cairo surface handling and Pixman
into libc's buffer-fill path. This establishes software painting/compositing and buffer filling
on the UI thread as the expensive work in those intervals. Loaded NVIDIA libraries
and an open render device alone would not establish that attribution.

Disassembly of the hot libc addresses shows repeated vector stores of the same
register into the destination buffer, a fill/clear loop rather than a copy from a
second buffer. Most system libraries are stripped. `addr2line`'s nearest exported names are not
reliable names for private functions, so no exact private GTK function name or
source line is claimed. In particular, the profile does not establish a specific
application CSS animation, JavaScript frame loop or Svelte update as the trigger.

Temporary breakpoints on three public redraw/phase-request entry points did not
fire during a bounded twenty-second attachment. This probe was inconclusive; it
does not rule out an already-running frame clock, a different invalidation path or
a state change caused by pausing the process.

## Isolated comparisons and the benchmark gap

The preserved binary was measured with the existing harness, a short document and
a library of 1,000 files: **30 ms CPU over fifteen seconds** across all three app
processes, about **0.2% of a core combined**. That result is real for that test.

The harness sets `BISMILLAH_TEST`. The editor consequently uses
`drawSelection({ cursorBlinkRate: 0 })`. Xvfb also starts without window focus, and
`scripts/headless.sh` sets `WEBKIT_DISABLE_DMABUF_RENDERER=1`. These conditions differ
from the author's native Wayland session. The earlier budget already noted the
unfocused caret, but its result must not be generalized to all live idle states.

A separate X11 comparison focused the private window and restored the normal
1.2-second CSS caret blink. In twelve-second intervals, the main process/renderer
were approximately 1.08%/0.58% with a steady caret, 2.75%/1.17% with blinking, and
1.50%/0.67% with the animation disabled. The initial background interval was higher
(17.74%/1.42%), so startup and warm-up are confounders. These are diagnostic samples,
not a release-budget measurement or proof that blinking explains the live heat.

A fresh copy of the same binary was also launched through the private harness onto
hidden workspace 99, using native Wayland, normal non-test caret behaviour, private
settings/data and a synthetic document. Its main-process threads used about 0–0.07%
CPU over fifteen seconds. It exited after sampling. A hidden fresh window does not
reproduce the long-running window's visible/focus/rendering history.

## Questions at the initial investigation

bounded blink remains separate from that temporary workaround.

- Compare the same document, window size and visibility with and without the DMA-BUF

- Extend the performance gate to cover native/focused idle behaviour. Keep the

  build may reduce application-code overhead, but the current Rust debug profile

## Follow-up: candidate caret mitigation and mode comparisons

`src/editor/caretBlink.ts` replaces CodeMirror's infinite, stepped CSS caret
animation with one visibility change every 600 ms. It preserves the 1.2-second
cycle for eight cycles (9.6 seconds), then rests visibly until typing, selection movement or regained focus. It uses no
editor transactions or layout measurements. It cancels its timer when unfocused,
hidden, read-only, under reduced motion, or destroyed; screenshot mode stays steady.
This removes the confirmed continuous-animation source without disabling grammar,
transliteration or hardware rendering. The live workaround below exercises the
same animation removal; it keeps the existing process steady until restart.

The real-app harness now has a `blinkCaret` test hook. The optional focused-caret
benchmark explicitly focuses its private X11 window, requires CSS animation `none`,
counts actual blink visibility edges, and checks that edges stop both after the idle timeout and after blur:

```bash
pnpm perf -- --binary target/debug/bismillah --parts caret --idle 15
```

This focused X11 measurement still does not establish native Wayland/GPU performance.
A scratch native Wayland WebDriver comparison failed to establish an automation
session and produced no CPU comparison; it is not evidence for or against the fix.

The author's grammar/transliteration hypothesis was checked separately using
the preserved pre-mitigation executable, the sample document, focused X11 and the
harness's steady caret. The first probe used incorrect settings keys (`grammar`
instead of `check_grammar`) and its comparison is invalid; those figures are not
mode-comparison evidence. The corrected probe checks Rust's settings snapshot after
every change and records the active grammar value and visible transliteration mode.


A warmed-up, alternating comparison in the same focused X11 instance measured the
original CSS animation against the continuously blinking opacity prototype (before the idle timeout was added), with 15-second
samples and five seconds between phases:

| Phase | Main CPU | Renderer CPU |
|---|---:|---:|
| CSS animation, first | 3.00% | 1.40% |
| Discrete opacity, first | 2.80% | 1.20% |
| CSS animation, repeat | 2.87% | 1.47% |
| Discrete opacity, repeat | 2.53% | 1.13% |

This is a modest improvement in this harness, not an explanation for 50–70% native
main-process use. A first candidate used `visibility` and recorded a high initial
focused sample (2,440 ms CPU/15 s); it was replaced with opacity updates and a
composited caret layer. The retained implementation's repeated results are above.
The benchmark also warms up for ten seconds before each focused/unfocused sample.
Artifacts: `/tmp/bismillah-caret-ab-results.json`.

The test harness can now count actual word-counter computations and pause them
through `wordCounter()`; Rust's test-mode flag gates that probe. It also exercises
transliteration through the workspace command, keeping the text conversion, status
indicator and native menu in agreement. The previous `setTransliteration` hook
changed only the editor state and left the indicator stale; that harness bug is
fixed. No user-facing transliteration algorithm or word-count algorithm changed.


The final mode comparison used the real transliteration command, verified the
visible mode indicator, and checked Rust's `check_grammar` value. Spelling remained
on; each phase waited for checking to settle and then warmed up for five seconds.
Fifteen-second CPU samples from the preserved, pre-mitigation binary:

| Mode | Main CPU | Renderer CPU |
|---|---:|---:|
| Grammar off, transliteration off (initial) | 1.40% | 0.73% |
| Grammar on, transliteration off | 1.47% | 0.73% |
| Grammar off, transliteration on | 1.47% | 0.73% |
| Both on | 1.40% | 0.60% |
| Both off (repeat) | 1.40% | 0.73% |

There is no meaningful idle CPU increase attributable to either feature in this
sample. This does not rule out checking cost after edits, long documents, or a
native-window-specific interaction. Transliteration itself contains no timers or
recurring background work; it operates on typed input. The checker works through
dirty blocks and becomes idle once they finish. The final validated results replace
the earlier invalid-key probe: `/tmp/bismillah-mode-idle-results.json`.

For the word counter, the probe observed one computation after a deliberate scratch
edit, then zero during the enabled idle interval. Enabled and paused intervals both
used about 1.33% main and 0.60% renderer CPU. This rules out repeated counting in
that tested idle state; it does not establish the cause of the hot native window.


Hiding just the displayed word/reading-time labels also left idle use essentially
unchanged (1.40% main / 0.60% renderer); restoring them gave 1.47% / 0.60%. All four
counter intervals recorded zero count computations. Resuming the paused counter
caused exactly one refresh before the next sample, as intended. Artifact:
`/tmp/bismillah-counter-idle-results.json`.

The real-app caret regression checks blinking, focus loss/return, typing and undo,
no word counting during idle blinking, and caret alignment in vocalised Arabic at
640/1280/1920/2560 CSS px, both themes, including 200% at 640. All five passed, and all
eight screenshots in `/tmp/bismillah-caret-shots/` were inspected: no clipped marks,
misaligned caret or altered text. The design review passes with the note that native
Wayland CPU acceptance remains open. The eight unit cases cover blink timing and
resting, typing/movement resets, visibility, focus loss, reduced motion, read-only/
steady mode and destruction cleanup.

The first full-gate attempt exposed an existing over-specific frontmatter click
assertion: a block-widget click may map to its closing source boundary (offset 30),
which is valid and reveals the metadata, but the test required an offset below 20.
The test now checks against the closing delimiter and still requires the folded
widget to disappear. The keyboard-specific assertion remains unchanged.


## Native cause confirmed and running app cooled

The live process was still PID 3078504. The native debugger queried only GTK widget
metadata and the caret's computed animation/focus state. Calls were made at a GTK
event-loop boundary; asynchronous WebKit results were checked through a temporary
WebKit title marker containing only animation/focus metadata, then the original
title was restored. No document contents were read or changed.

The verified initial state was `animation-name: cm-blink`, duration `1.2s`,
`document.hasFocus() === false`, no `cm-focused` editor class, and
`document.hidden === false`. Hiding the caret strokes when unfocused had not stopped
the animation on their parent layer.

A stylesheet rule, rather than an inline style that editor updates can overwrite,
disabled the animation in the same live process. Ten-second CPU intervals:

| Native state | Main CPU | WebKit renderer CPU |
|---|---:|---:|
| Original animation, unfocused | 54.80% | 11.20% |
| Animation disabled | 0.20% | 0.10% |
| Animation restored | 47.80% | 8.00% |

This A/B/A result ties the high CPU to the caret animation and explains the earlier
GTK/Cairo/Pixman painting profile. It does not establish an exact frame rate or
WebKit's internal scheduling mechanism. Later intervals varied; one further
animation-disabled interval recorded 18.1%/5.5%, and the window was focused by the
final metadata check. That changing-focus interval is not used for the claimed
idle reduction. Earlier inline-style probes without computed-style verification
were inconclusive and are not the basis for this conclusion.

After restoring the experimental changes, a dedicated steady-caret workaround was
applied to the author's still-running window, with its actual computed style
verified as `animation: none` while unfocused. The next ten-second sample was
**0.10% main CPU, 0% renderer CPU, 0% network-process CPU**. This rule is in memory
only, lasts until the app exits, and leaves the document and all checking features
unchanged. The rebuilt app supplies the permanent bounded blink rather than this
always-steady temporary caret.

Artifacts: `/tmp/bismillah-live-caret-verified.json`,
`/tmp/bismillah-live-caret-fixed.json`, and the metadata-only debugger probe logs in
`/tmp/bismillah-live-caret-mode-*.log`.

The full-suite geometry check also depended on recovery notices left by earlier
crash tests. Its fixture now defers those notices with *Not now* before measuring
the writing area, retaining recovery files on disk. The focused-caret spec restores
its original private X focus and window size on exit. These are test-isolation
fixes; recovery behaviour in the application is unchanged.
