# The stick's 1.0 security audit (2026-10-22)

The short security audit of os/PLAN.md Phase OS-5, for the bismillah stick's 1.0: the ways out of the editor, the helper's socket, the laptop left untouched, reflashing, and what the image contains. Everything here ran on the author's machine, in QEMU with OVMF and Secure Boot on (Microsoft's 2011 and 2023 CAs), on the images the commit that records it builds. The release image is observed only from outside; the debug image, which boots the same way but has a root command line on a serial port, is inspected from inside.

The threat model is the plan's: **a lost or stolen stick** (powered off), and **no traces on the host laptop**. A secretly modified stick and a hostile laptop are out of scope, and stay listed under *Not covered*.

Each section says what was checked, how, what it found, and what changed because of it. Where a check runs on every build, its name in `os/scripts/test.ts` (a VM scenario), `os/tests/image-contents.ts` (the contents check) or the app's tests is given.

## Ways out of the editor

The writer's session is cage running bismillah, as uid 1000, with no password. The question for each item: can it reach a shell, another program, or a file outside the encrypted library?

| Way out | How it was checked | Result |
|---|---|---|
| systemd-boot's menu and editor | Keys held while the loader starts (`ways-out`); `loader.conf` (contents) | No menu and no editor. **Changed:** `timeout 0` let a held key open the menu; it is now `timeout menu-disabled`, with `editor no` and `auto-firmware no`. |
| The kernel command line | The boot entry (contents) | Only the entry's own options; nothing names a shell, `init=`, a unit or `rd.break`. The firmware could pass shim other options (below, *Not covered*). |
| Emergency and rescue shells | Units (contents); the initrd's files | Masked in release, and neither the system nor the initrd has `sh`, `bash`, `dash`, `sulogin` or `login`. A failed boot stops; it never opens a shell. |
| VT switching | Ctrl+Alt+F2, F3, F6 in the session (`ways-out`) | Nothing happens: cage switches VTs only with `-s`, and no getty runs on any VT (`NAutoVTs=0`). |
| Magic SysRq | Alt+SysRq+B, O, C in the session (`ways-out`); `/proc/sys/kernel/sysrq` | Nothing happens. **Changed:** `sysctl.d` set it to 0 only once the system had started; Debian's kernel allowed most SysRq keys until then. `sysctl.kernel.sysrq=0` on the command line now covers the initrd too. |
| Ctrl+Alt+Del | In the session (`ways-out`); the target (contents) | In the session the keys reach the app, which ignores them. On an empty VT (the lock's fallback) the kernel passes them to systemd. **Changed:** that restarted the machine; it now powers off cleanly, and pressing it repeatedly does nothing more drastic (`CtrlAltDelBurstAction=none`). mkosi's presets kept re-aliasing the target to reboot, so a finalize script sets it. |
| Ctrl+Alt+Backspace | `ways-out` | Nothing happens. |
| WebKit's inspector | F12, Ctrl+Shift+I, J, C (`ways-out`); the release build | Developer extras are off in release builds (wry enables them only with `devtools`), and no unit sets `WEBKIT_INSPECTOR_*` (contents). |
| WebKit's own context menu | The appliance e2e | **Found:** outside the editor, a right-click opened WebKit's page menu with *Reload*. A reloaded page met no gate, because the app had already started, and nothing told it the stick was locked: **the reload showed the text without the passphrase.** **Changed:** on the stick the page menu is suppressed (fields and the editor keep theirs), and any page loaded after the app started opens behind the lock view. The e2e fails without the fix. |
| A browser's keys (F5, Ctrl+L, F6) | `ways-out` | Nothing happens: WebKitGTK binds none of them. |
| The native Open, Save as, New file and Open folder dialogs | Rust tests (`appliance::tests`); the appliance e2e | GTK's chooser can browse the read-only system and type any path, but launches nothing. **Found:** a path typed by hand, such as `/tmp/note.md`, was accepted. The text was then saved in RAM: shown as saved, gone at power-off. **Changed:** on the stick, Rust refuses any dialog path, dropped file or folder outside `~/Texts`, with symlinks resolved. The writer reads *only the library is kept on the stick*. |
| Drag and drop | Code review | Only the app runs, so nothing else can drag a file in; a drop goes through the same library check. |
| Opening links and the file manager | `link_open`, `folder_show` (Rust) | Refused in appliance mode, and the image has no `xdg-open`, `gio` or terminal (contents). |
| Other programs | Contents | No shell, interpreter (`perl`, `python3`), `busybox`, `su`, `sudo`, `login`, `agetty`, `apt` or `dpkg`. |
| Programs with more rights | Contents (new: a second extraction that keeps modes) | **Found:** `mount` and `umount` were setuid root, as Debian ships them. The writer never mounts; the helper does, as root. **Changed:** the bit is removed at build. What remains is `unix_chkpwd` (setgid shadow), which PAM runs when the session starts. Nothing in the image is writable by anyone. |

## The helper's socket

The helper is the only process running as root that takes requests. It listens on `/run/bismillah/helper.sock` (owner `writer`, mode 0600) and checks the peer's uid with `SO_PEERCRED`.

**How:** `helper-socket` runs the debug image's new probe (`bismillah-probe`, built only with the debug feature) as root, as `nobody` and as the writer, then 3 000 damaged request lines and a connection that sends nothing. A unit test feeds the parser 200 000 damaged lines (`damaged_lines_are_refused_or_only_ask`). The damaged lines start from requests that change nothing, so a fuzz run can't format or power off the VM.

**Result:**
- Root (uid 0) connects but gets no answer; `nobody` can't connect (`PermissionDenied`); the writer is answered.
- 3 000 damaged lines: 2 985 refused (`failed`), and 15 that still read as status requests answered with the status. The helper then answered a status request, and the app kept running.
- No damaged line parsed as anything but a status request, in either run. Lines longer than 16 KiB are cut off at 16 KiB and refused.

**Found and changed:** the helper serves one connection at a time, and a client that connected and sent nothing held it up indefinitely, the lock before sleep included. A client now has 5 s to send its request (measured: the next request was answered after 5.3 s); the events connection, which stays open, is exempt.

## The laptop left untouched

**How:** `host-untouched` boots the release image beside a laptop disk (NVMe: an ESP, an ext4 root, a swap partition and a decoy ext4 partition of the home type labelled `bismillah-home`) behind a qcow2 overlay. It sets the stick up, writes, and powers off. QEMU stays after the power-off, so its write counters can be read; the overlay is then mapped, and the firmware's variable store is compared with the one it started from. The debug image repeats the boot and shows from inside what was mounted, swapped to and mapped.

**Result:**
- Release: **0 write requests** to the laptop's disk (316 reads, for partition probing), and no cluster of its overlay allocated. Debug: 0 writes as well.
- Firmware variables changed: `SbatLevel`; and OVMF's `Boot0000`–`Boot0002`, `BootOrder`, `ConIn`, `ConOut`, `ErrOut`, `Key0000`, `Key0001`, `Lang`, `PlatformLang`, `MTC`, `Timeout`, `VarErrorFlag`, `VendorKeysNv`, `certdb` and `MemoryTypeInformation`. The VM starts from a fresh variable store, so the firmware's own first-boot bookkeeping is in the list too. `SbatLevel` is shim's, and the README discloses it; the rest is OVMF's own (a boot entry for the stick, its bookkeeping).
- Inside: no swap in use, nothing of the laptop's disk mounted, only the stick's `root` and `home` mapped, no RAID assembled, and home on the USB stick rather than the decoy. lvm2 and mdadm aren't installed, and the release image has no `swapon`.
- `no-network` (unchanged since OS-1): zero frames on a virtio, a PCIe and a USB network card, the last two plugged in while the stick ran.

## Reflashing

**How:** `node --test os/tests/stick.test.ts` runs the reflash tool on made-up sticks. `reflash` sets a stick up on the debug image and saves a text, then replaces its system with the release image, which unlocks it, and with the debug image again.

**Result:**
- Debug, then release, then debug: each update wrote the root (640 MiB), the verity (8 MiB) and the ESP (512 MiB), and read all three back. Home's first 16 MiB (its LUKS2 header and more) were unchanged, and the stick kept its own GUIDs and stick-id. The release system unlocked the home the debug system had set up, and the debug system found the text intact, its new root verified.
- The tool refuses a stick whose GUIDs aren't in the registry, a twin with another stick's GUIDs but its own stick-id, a disk with a partition missing or of another type, and a system bigger than the stick's slots, each before writing anything. An update interrupted while writing the ESP can be run again.

**Found and changed:** every stick flashed from one image had the same disk and partition GUIDs. That made two sticks twins, which the helper refuses. On the Dell, the ESP's GUID once matched an old firmware boot entry, which hid the stick from its boot menu. The first flash now gives each stick its own disk, ESP and home GUIDs. Root and verity keep the build's GUIDs, because the boot finds them by the root hash.

## The image's contents

The contents check runs on every build of both images. Besides what earlier phases added (no network drivers or firmware, every file traced, declared or needed, no getty, masked TPM and journal units), OS-5 adds the ways out above: no shells in the initrd, no launchers, terminals, LVM, RAID or swap tools, the command line's options, the loader's settings, the stick-id placeholder, Ctrl+Alt+Del, and the permission check.

The release image has 3 165 files and 925 links. Its programs are bismillah, its helper, cage and `wlr-randr`; systemd's, udev's and D-Bus's; the helper's tools (`cryptsetup`, `dmsetup`, `mke2fs`, `e2fsck`, `blkid`, `lsblk`, `mount`); and kmod's. The only program with more rights than its caller is `unix_chkpwd` (setgid `shadow`), and nothing is writable by anyone.

## Not covered

- **A modified stick.** The initrd and the kernel command line aren't signed in this boot chain, so someone with the stick could change them, or the system, to capture the passphrase. Out of scope by the author's choice; signed UKIs with the author's own keys are a later item.
- **Options passed by the firmware.** Firmware with a UEFI shell, or a boot entry carrying load options, could pass shim a different second stage or options. This needs the laptop's firmware set up for it: the hostile laptop case.
- **A hostile laptop:** its firmware, a hardware keylogger, a device that injects keystrokes. A keystroke injector reaches only the editor, but it can type into it and save.
- **Memory attacks** on a stick that is running or suspended (DMA, cold boot): the disk key is in RAM. The Thunderbolt driver is kept, for docks and their keyboards; the kernel's IOMMU defaults apply.
- **What GTK's file chooser can read:** the read-only system, and the writer's own home. Nothing secret is on the system, and only uid 1000's files are readable.
