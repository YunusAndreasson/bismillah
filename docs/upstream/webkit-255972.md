# Draft comment for WebKit bug 255972

*Drafted 2026-10-18 for [bug 255972](https://bugs.webkit.org/show_bug.cgi?id=255972) ("[Harfbuzz] Some Arabic fonts are not being shaped correctly"), as ADR-0011 decided. **Not posted.** The author posts it from their own WebKit Bugzilla account.*

The bug has no root cause yet: it holds the reporter's screenshots (Noto Nastaliq Urdu, Mada, Noto Sans Arabic; later Noto Naskh Arabic, Reem Kufi, Aref Ruqaa, Gulzar) and a maintainer's question about whether the Skia switch in 2.46 changed things. The comment below adds what's missing: a minimal reproduction on current WebKitGTK, the cause in the Skia text path, numbers, and a patch.

**The patch is untested against a WebKit build.** It was written against `main` at 7b54846607 (2026-10-18; `FontSkia.cpp` last changed in 00ef3983cae0) and reasoned from the source. Say so when posting.

**Why we think the fix is right.** `ComplexTextController::advance()` makes each glyph's paint advance point from that glyph's origin to the next glyph's origin, so the paint heights are −(o₁−o₀), −(o₂−o₁), … (y down), and `layoutComplexText()` starts the run at −o₀. Today Skia draws every glyph at that start, so glyph *k* lands at −o₀ instead of −oₖ: the first glyph's offset applied to the whole run. That model predicted WebKit's ink heights in our spike to within 0.6px. With accumulated heights, glyph *k* lands at −o₀ + (o₀ − oₖ) = −oₖ, its HarfBuzz position.

## Comment

This still happens with WebKitGTK 2.54.1 (Skia), and I think I've found the cause: on the Skia path, the vertical glyph offsets that HarfBuzz gives combining marks are dropped when the text blob is built. A patch is attached; I haven't been able to build WebKit with it, so please treat it as a pointer rather than a tested fix.

**Reproduction** (any font that positions marks with GPOS y offsets; Noto Naskh Arabic, Amiri and IBM Plex Sans Arabic all show it):

```html
<!doctype html>
<meta charset="utf-8">
<style>
  p { font: 64px/2.5 "Noto Naskh Arabic", "Amiri", serif; margin: 0; }
  .pre { white-space: pre-wrap; }
</style>
<p dir="rtl" lang="ar">لِلَّهِ عَلَىٰ بِسْمِ ٱللَّهُ الرَّحْمَٰنِ قُلْ</p>
<p dir="rtl" lang="ar" class="pre">لِلَّهِ عَلَىٰ بِسْمِ ٱللَّهُ الرَّحْمَٰنِ قُلْ</p>
```

**Expected:** both lines look the same, with every mark where HarfBuzz places it (as in Firefox and Chromium).

**Actual** (attached screenshot, Noto Naskh Arabic 2.021 from Arch's noto-fonts 2026.10.01): marks, and in this font the letter dots too, sit where the font draws them instead of where GPOS moves them: the shadda–fatha stacks, the dagger alif on عَلَىٰ, the dot and kasra of بِسْمِ, the dot of the final ن. Measured against HarfBuzz, each word's ink top or bottom is 0.08–0.17 em off in the `normal` line. In the `pre-wrap` line each word is its own run, so a word whose leftmost glyph is a mark also moves as a whole: عَلَىٰ drops by 0.6 em, leaving its fatha and dagger alif behind.

**Cause.** `FontBase::buildTextBlob()` in `Source/WebCore/platform/graphics/skia/FontSkia.cpp` builds horizontal runs with `SkTextBlobBuilder::allocRunPosH()`, which stores x positions only. The glyph advances it receives do carry the vertical offsets: `ComplexTextController::advance()` folds each glyph's origin (HarfBuzz `x_offset`/`y_offset`, from `ComplexTextRun` in `ComplexTextControllerHarfBuzz.cpp`) into the paint advances, height included, and flips them so that increasing y points down. `FontCascade::drawGlyphBuffer()` honours those heights when it moves the start point between fonts, and the Core Text path accumulates them into glyph positions (`fillVectorWithHorizontalGlyphPositions()` in `FontCascadeCoreText.cpp`). `buildTextBlob()` accumulates the heights in `glyphPosition` but never writes them for horizontal text, so:

- every glyph is drawn at the run's starting y, which `layoutComplexText()` derives from the first glyph's origin through the initial advance, so marks lose their own y offsets;
- with `white-space: pre`, `pre-wrap` or `break-spaces` the text is painted one run per word, so a word whose first visual glyph is a mark is drawn shifted by that mark's offset.

That would explain the pattern reported here: fonts that draw most marks in place need few y offsets and look nearly right (as reported here for Noto Sans Arabic since 2.47), while fonts that rely on GPOS y offsets (Mada, Noto Naskh Arabic, Reem Kufi, and the Nastaliq fonts, whose letters also climb diagonally) don't.

**Numbers** (WebKitGTK 2.54.1, `white-space: pre-wrap`, 237 vocalised words from Qur'anic text and modern prose, ink top and bottom of each word compared with HarfBuzz 14.6 and the fonts' glyph bounds; a word counts as wrong when an edge is off by more than 0.08 em):

| Font | Words wrong | Median error | Max |
|---|---:|---:|---:|
| IBM Plex Sans Arabic | 216 / 237 | 0.22 em | 1.09 em |
| Amiri | 44 / 237 | 0.01 em | 0.79 em |
| Amiri Quran | 39 / 237 | 0.02 em | 0.65 em |

For لِلَّهِ in Amiri at 40px the leftmost glyph is the kasra (y offset +181 units), so the whole word is drawn 7px high and the shadda and fatha offsets (−164, −215) are lost; a model of exactly that predicts WebKit's ink heights to within 0.6px.

**Proposed fix** (attached): when any advance in the run has a height, build the horizontal run with `allocRunPos()` and write each glyph's accumulated (x, y), keeping `allocRunPosH()` as the fast path for runs without vertical movement, which is nearly all non-complex text. With the heights `ComplexTextController::advance()` produces, glyph *k* is then drawn at the run's start y plus the sum of the earlier heights, which telescopes to its own HarfBuzz y offset.

While reading this I also noticed that for LTR complex runs `layoutComplexText()` passes the first glyph's origin into the initial advance without the y flip that `advance()` applies to paint advances; it only matters when an LTR run starts with a vertically offset glyph, and I haven't verified it.

Thank you for WebKitGTK; we're building a small offline Markdown editor on it, and Arabic with full vocalisation is central to its writers.
